# Занятие 2.3. Таблица виртуальных вызовов и движок правил

> [Лекция 7](../lectures/07/lecture.md): виртуальные функции, абстрактные классы, виртуальный деструктор,
> `enum class`.

До сих пор условие, правило и источник событий были конкретными типами.
`Condition` выбирал вид сравнения через `switch`, агент хранил
`std::vector<MatchRule>`, а `main` выбирал между двумя источниками веткой
`if`, где каждый источник назван своим типом. На этом занятии все три места
уходят за интерфейсы: классы, в которых объявлены только
[чисто виртуальные функции](../lectures/glossary.md#pure-virtual) (pure
virtual functions). Код, который пользуется интерфейсом, перестаёт знать,
с каким наследником он работает.

Это даёт две вещи, которых раньше не было: условие, составленное из других
условий, и правило с состоянием, которое ловит атаку из двух событий. На
`phishing_macro` агент под `--quiet` печатает на одну строку больше, чем
на 2.2:

```
[DETECT] high  script_host_from_temp  ts=1730000003000 pid=1101
[DETECT] critical  script_host_beacon  ts=1730000004200 pid=1101
[DETECT] medium  hidden_powershell  ts=1730000006000 pid=1156
```

Вторая строка — новое правило: скриптовый хост через 1,2 секунды после
запуска открыл сетевое соединение. Такая же строка добавляется
в `pid_reuse`, а на остальных пяти сценариях вывод не меняется.

### 1. Условие за интерфейсом

В [`conditions.h`](../project/kit/include/l2.3/conditions.h) объявлен
интерфейс `ICondition` с одной
[виртуальной функцией](../lectures/glossary.md#virtual-function) (virtual
function) `Matches`:

```cpp
class ICondition {
 public:
    virtual ~ICondition() = default;
    virtual bool Matches(const Event& event) const = 0;
    bool operator()(const Event& event) const { return Matches(event); }
};
```

Каждый вид сравнения — свой наследник, и `Matches` в нём
[переопределяется](../lectures/glossary.md#override) (overriding) со словом
`override` ([лекция 7, раздел 3](../lectures/07/lecture.md#3-override-и-final)).
`switch` по виду сравнения уходит вместе с `Condition`: чтобы добавить новый
вид, пишут новый класс и не трогают существующие.

В `src/conditions.cpp` пишется `Matches` пяти простых условий:

| Класс | `Matches` возвращает `true`, если… |
|---|---|
| `FieldEquals(key, value)` | …значение поля `key` равно `value` |
| `FieldContains(key, needle)` | …значение поля `key` содержит `needle` |
| `FieldEndsWith(key, suffix)` | …значение поля `key` заканчивается на `suffix` |
| `FieldInList(key, values)` | …значение поля `key` равно одному из `values` |
| `EventTypeIs(types)` | …`event.event_type()` — один из `types` |

Первые четыре вы уже писали: это `operator()` функторов с занятия 2.2, тела
переезжают в `Matches` без изменений. Правила те же — регистр
не учитывается, поле ищется через `FindField`, отсутствующее поле
и пустой список дают `false`. `operator()` написан в `ICondition` один раз
поверх `Matches`, поэтому тесты набора 2.1, которые зовут условия как
функторы, продолжают компилироваться.

**`EventTypeIs` сравнивает перечисления, а не строки.** В
[`event.h`](../project/kit/include/l2.3/event.h) появился `EventType` —
[scoped enumeration](../lectures/glossary.md#scoped-enum), перечисление
`enum class` ([лекция 7, раздел 8](../lectures/07/lecture.md#8-enum-и-enum-class)),
и метод `Event::event_type()`. Опечатку в имени значения перечисления
заметит компилятор, а строку `"proces_start"` он пропустит молча. Поле
`event_type_` заполняет ваш конструктор `Event` в `src/event.cpp`, и там же
пишутся две функции:

| Функция | Что делает |
|---|---|
| `EventTypeFromString(type)` | `"process_start"` → `kProcessStart`, и так для всех семи типов из [`SPEC.md`](../project/SPEC.md); незнакомая строка → `kOther`, а не исключение |
| `EventTypeName(type)` | обратно: значение → строка; `kOther` → `"other"` |

Конструктор `Event` вызывает `EventTypeFromString` и кладёт результат
в `event_type_`. Строка типа при этом сохраняется: по `kOther` не поймёшь,
что пришло, а по `type()` поймёшь.

### 2. Условие из условий

Два оставшихся класса в `conditions.h` — составные условия. Они хранят
другие условия как `std::unique_ptr<ICondition>` и ничего не знают об их
видах:

| Метод | Что делает |
|---|---|
| `AllOf::Add(condition)`, `AnyOf::Add(condition)` | добавляет условие в конец |
| `AllOf::Matches(event)` | `true`, если все вложенные условия вернули `true` |
| `AnyOf::Matches(event)` | `true`, если хотя бы одно вернуло `true` |

Пустой `AllOf` возвращает `true`, пустой `AnyOf` — `false`
([почему](#почему-пустой-anyof-ложь)). Составные условия вкладываются друг
в друга: `AnyOf` может лежать внутри `AllOf` и наоборот.

Переключатель такого не выражал вовсе. Из-за этого на 2.2 правила
`autostart_write` и `ransom_extension` записывались двумя объектами
с одним идентификатором: «`path` заканчивается на `.locked` **или** `to`
заканчивается на `.locked`» в одно правило не помещалось. С `AnyOf`
помещается:

```cpp
auto rule = std::make_unique<MatchRule>("ransom_extension",
                                        Severity::kCritical);
rule->AddCondition(std::make_unique<EventTypeIs>(std::vector<EventType>{
    EventType::kFileCreate, EventType::kFileWrite, EventType::kFileMove}));

auto paths = std::make_unique<AnyOf>();
paths->Add(std::make_unique<FieldEndsWith>("path", ".locked"));
paths->Add(std::make_unique<FieldEndsWith>("to", ".locked"));
rule->AddCondition(std::move(paths));

rule->AddAction("quarantine_file");
```

Список значений внутри одного условия, как в `Condition::Contains("cmdline",
{...})` на 2.2, тоже записывается через `AnyOf`: по `FieldContains` на каждое
значение.

### 3. Правило за интерфейсом и движок

В [`rule.h`](../project/kit/include/l2.3/rule.h) над `RuleBase` появился
интерфейс `IRule`: `id()`, `severity()`, `Check`, `hits()` и `actions()`, все
чисто виртуальные. `IRule` — [абстрактный класс](../lectures/glossary.md#abstract-class)
(abstract class): создать его объект нельзя, можно только указатель или
ссылку на наследника ([лекция 7, раздел 4](../lectures/07/lecture.md#4-абстрактные-классы)).
`RuleBase` реализует общее, `MatchRule` наследует `RuleBase`, как на 2.2.
`Check` не `const`: правилу разрешено помнить прошлые события, и на шаге 5
появится такое правило.

Условия правило теперь получает во
[владение](../lectures/glossary.md#ownership) (ownership): `AddCondition`
принимает `std::unique_ptr<ICondition>`, и освобождает условие деструктор
правила.

В `src/rule.cpp` пишется:

| Метод | Что делает |
|---|---|
| `RuleBase(id, severity)`, `AddAction(action)` | как на 2.2 |
| `MatchRule(id, severity)` | как на 2.2 |
| `AddCondition(condition)` | добавляет условие в конец `conditions_` |
| `MatchRule::Check(event)` | `true`, если все условия вернули `true`, — тогда же зовёт `CountHit()`; у правила без условий всегда `true` |

Новое — движок, [`rule_engine.h`](../project/kit/include/l2.3/rule_engine.h).
Он владеет правилами и прогоняет через них событие; в `src/rule_engine.cpp`:

| Метод | Что делает |
|---|---|
| `AddRule(rule)` | добавляет правило в конец `rules_` |
| `ProcessEvent(event, fired)` | зовёт `Check` у каждого правила в порядке добавления и возвращает, сколько сработало. Если `fired` не `nullptr`, **дописывает** в него указатели на сработавшие правила; что там было до вызова, остаётся |

Печати в движке нет: он сообщает, какие правила сработали, а печатает агент
([почему](#почему-движок-не-печатает)).

**Набор правил.** Пять правил с занятия 2.2, но объектов теперь тоже пять:
`autostart_write` складывается в одно правило так же, как `ransom_extension`
в [шаге 2](#2-условие-из-условий). `RuleEngine` нельзя копировать, поэтому
вернуть его из функции, как `BuildAgentRules()` возвращала вектор, не выйдет.
Замените `BuildAgentRules()` функцией, которая заполняет движок, например:

```cpp
void RegisterAgentRules(RuleEngine* engine);
```

**Агент.** Поле `std::vector<MatchRule> rules_` заменяется на
`RuleEngine engine_`, и конструктор агента заполняет его набором правил.
`HandleEvent` зовёт `engine_.ProcessEvent(event, &fired)` и печатает строку
детекта для каждого правила из `fired` — тем же форматом, что раньше. Сводка
берёт правила через `engine_.size()` и `engine_.rule(i)`.

**Заглушки для `SequenceRule`.** Тесты набора 2.3 зовут и `SequenceRule`,
которое пишется на [шаге 5](#5-правило-на-два-шага), и без его методов
не слинкуются. Чтобы проверить шаги 1–3 сейчас, заведите в `src/rule.cpp`
пустые тела: конструктор передаёт идентификатор и важность `RuleBase`,
`SetFirst` и `SetSecond` ничего не делают, `Check` возвращает `false`.

**Проверка.** Проект и тесты собираются, наборы 2.1 и 2.3 зелёные, кроме
тестов `SequenceRule`. Вывод под `--quiet` на всех семи сценариях совпадает
с эталонами занятия 2.1:

```bash
./build/linux/nano-edr --quiet scenarios/phishing_macro.log > out.txt
diff out.txt tasks/2.1/tests/expected/phishing_macro.out
```

На Windows — `./build/windows/Release/nano-edr` и `fc.exe`. Эталоны 2.1
годятся и сейчас: на 2.2 вывод не менялся. В сводке правил стало пять
строк вместо семи.

### 4. Источник за интерфейсом

В [`event_source.h`](../project/kit/include/l2.3/event_source.h) два
интерфейса. `IEventSource` — откуда берутся события, у него один метод
`Run(handler)`. `IEventHandler` — кому они отдаются. Источник знает только
`IEventHandler`, агент не знает, какой источник его вызывает.

Агент становится наследником `IEventHandler`, и его методы переименовываются
в методы интерфейса:

| Было на 2.1 | Стало |
|---|---|
| `HandleEvent(event)` | `HandleEvent(event) override` |
| `CountSkipped()` | `OnSkipped() override` |
| `CountBroken()` | `OnBroken() override` |
| `Tick()` | `OnTick() override` |

`FileSource` и `OsSource` становятся наследниками `IEventSource`, а их
`Run(Agent*)` — `Run(IEventHandler*) override`. `sources.h` больше
не включает `agent.h`.

**Трамплин приводит `void*` к тому же типу, что передан в `Subscribe`.**
`OsSource::Run` теперь передаёт в `Subscribe` указатель на
`IEventHandler`, значит и трамплин обязан привести `context`
к `IEventHandler*`, а не к `Agent*`. Это то же требование, что на занятии
2.1, и в упражнении 2.2 (часть 3) видно, почему адрес наследника и адрес
его базы бывают разными.

В `main` две ветви `if` с двумя вызовами `Run` сводятся к одной:
ветвь только создаёт нужный источник, а `Run` зовётся один раз, уже через
интерфейс:

```cpp
std::unique_ptr<IEventSource> source;
if (options.force_file) {
    source = std::make_unique<FileSource>(options.path);
} else {
    source = std::make_unique<OsSource>(options.path);
}
source->Run(&agent);
```

**Проверка.** Тесты `task2.1.sources.<журнал>` зелёные: они прогоняют агента
через оба источника на семи сценариях и на `rules_edges.log` и сравнивают
два вывода между собой. Если для этого шага пришлось править движок или
правила, интерфейс проведён не там.

### 5. Правило на два шага

`SequenceRule` из `rule.h` — правило с состоянием. Оно ищет пару событий:
сначала первый шаг, потом второй, не позже чем через `window_ms` и, если
включена связка по процессу, с тем же `pid`. Незавершённые совпадения —
первые шаги, которые ещё ждут второго, — лежат в `pending_`.

В `src/rule.cpp` пишется:

| Метод | Что делает |
|---|---|
| `SequenceRule(id, severity, window_ms)` | передаёт идентификатор и важность `RuleBase`, запоминает окно; связка по процессу включена |
| `SetFirst(condition)`, `SetSecond(condition)` | условия первого и второго шага |

`Check(event)` делает четыре вещи, и порядок существенный:

1. Если какой-то из шагов не задан, возвращает `false`.
2. **Вытесняет устаревшее.** Из `pending_` убирается каждое совпадение,
   у которого от первого шага до текущего события прошло больше
   `window_ms`. Без этого память правила растёт, пока агент жив.
3. **Закрывает совпадение.** Если событие подходит под второй шаг и
   в `pending_` есть совпадение с тем же `pid` (или связка выключена), оно
   снимается, вызывается `CountHit()`, и `Check` возвращает `true`. Одна
   пара — один детект: если не снимать, первый шаг даст детект на каждом
   следующем втором.
4. **Открывает совпадение.** Если событие подходит под первый шаг,
   в `pending_` добавляется его время и `pid`. Возвращается `false`.

Второй шаг проверяется раньше первого, чтобы событие, подходящее под оба,
закрывало начатое совпадение, а не начинало новое поверх себя.

Шестое правило в наборе — `SequenceRule`, добавьте его последним:

| | |
|---|---|
| Идентификатор | `script_host_beacon` |
| Важность | `Severity::kCritical` |
| Действие | `kill_process` |
| Первый шаг | запуск скриптового хоста: `process_start`, `image` заканчивается на `wscript.exe` или `cscript.exe` |
| Второй шаг | `net_connect` |
| Окно | 10 000 мс, связка по процессу включена |

**Проверка.** Тесты `SequenceRule` зелёные. В `phishing_macro` и `pid_reuse`
по сравнению с эталоном 2.1 добавилось **ровно по одной** строке
`script_host_beacon`. Две и больше — закрытое совпадение не снимается.

### 6. Ноль детектов на чистых сценариях

Прогоните `clean_office` и `clean_build`. На них детектов быть не должно:
правило, которое ловит атаку и заодно срабатывает на обычной работе, —
неработающее правило. Если детект есть, разберите, какое законное поведение
он поймал, и чем оно отличается от атаки в `phishing_macro`.

Починка не должна стоить истинных детектов. Правило, которое перестало
ошибаться потому, что перестало срабатывать вообще, не починено: строка
`script_host_beacon` в `phishing_macro` и `pid_reuse` остаётся. И чинить
надо смысл правила, а не подгонять его под строки журнала
([почему](#почему-правила-проверяют-на-чужих-журналах)).

**Проверка.** На `clean_office` и `clean_build` вывод под `--quiet`
пустой, в `phishing_macro` и `pid_reuse` новая строка на месте, остальные
пять сценариев совпадают с эталонами 2.1.

### 7. Цена невиртуального деструктора

Деструктор `IRule` виртуальный, и этот шаг показывает, что будет без этого.
Комплект менять нельзя, но здесь занятие разрешает **одну временную
правку**: в `kit/include/l2.3/rule.h` уберите слово `virtual` из строки

```cpp
virtual ~IRule() = default;
```

1. **Прочитайте предупреждение.** Соберите проект обычным пресетом. Clang
   предупредит, что `delete` вызывается для `IRule` с невиртуальным
   деструктором, но укажет он не на `rule.h` и не на ваш код, а на
   стандартный заголовок `<memory>`: удаляет правило `std::unique_ptr`.
   Ошибкой предупреждение не считается, и в длинном выводе сборки его легко
   не заметить.
2. **Прогоните тесты под [санитайзером](../lectures/glossary.md#sanitizer)
   (sanitizer):**

   ```bash
   cmake --preset asan-windows -D NANO_EDR_LESSON=2.3
   cmake --build --preset asan-windows
   ctest --preset asan-windows -R "task2.3|sources"
   ```

   На Linux — пресет `asan` и `ctest --preset asan` без `-R`. На Windows
   набор ограничен потому, что под `asan-windows` падает любой пойманный
   `throw`, — подробнее в
   [`project/README.md`, «Перед сдачей»](../project/README.md#перед-сдачей).
   Без вашей правки выбранные тесты проходят.

   Санитайзер остановит прогон с отчётом `new-delete-type-mismatch`: размер
   выделенного объекта и размер освобождаемого разные. Объясните оба числа:
   что лежит в объекте `MatchRule` и что — в `IRule`.
3. **Верните `virtual`.** Тест «у интерфейса правила виртуальный деструктор»
   снова зелёный, санитайзер молчит.

В [упражнении](#упражнение-диспетчеризация) компилятор на такой же ошибке
не предупреждает. Сравните `BadBase` из упражнения и `IRule`: чем они
отличаются и почему компилятору этого достаточно, чтобы заподозрить
ошибку в одном случае и промолчать в другом.

## Упражнение: диспетчеризация

[`tasks/2.3/exercise/dispatch.cpp`](../project/tasks/2.3/exercise/dispatch.cpp)
— отдельная программа, с агентом не связанная. Писать ничего не надо, обе
версии готовы: работа в том, чтобы прочитать их и **предсказать на бумаге**
три вещи, а потом сверить.

Таблицу указателей на функции вы уже писали — `Rule` с полем `RuleFn`
на занятии 1.3. Вызов через сохранённый указатель вместо жёстко названной
функции — это она и есть, и ровно так устроен `virtual`
([лекция 7, раздел 6](../lectures/07/lecture.md#6-таблица-вызовов-руками)).
Таблицу, которую компилятор строит сам, называют
[vtable](../lectures/glossary.md#vtable) (таблица виртуальных функций).
Отличий от занятия 1.3 два, и оба видны в коде: таблица здесь одна на тип,
а не одна запись на правило, и в функцию передаётся сам объект.

Упражнение собирается своей целью, как `inheritance` на занятии 2.2:

```bash
cmake --build --preset windows --target dispatch
./build/windows/Release/dispatch
```

На Linux — `--preset linux` и `./build/linux/dispatch`. Цель не зависит
от вашего кода в `src/`. Замер имеет смысл только в Release: в отладочной
сборке ничего не встроено, и обе версии одинаково медленные.

Что предсказать до запуска:

1. `sizeof` объекта с ручной таблицей и `sizeof` объекта с `virtual`.
2. Что напечатает счётчик незакрытых объектов, когда деструктор базы
   не виртуальный, — и почему компилятор об этом промолчал.
3. Что быстрее и во сколько раз.

Предсказание до запуска — не формальность: числа без догадки ничему
не учат, любые кажутся ожидаемыми.

Ещё четыре вопроса к этому коду:

- Почему таблица одна на «класс», а не одна на объект? Что было бы, если бы
  каждый объект хранил свою?
- В ручной версии `area` принимает `self` явным первым параметром. Куда он
  девается в версии с `virtual`?
- `ManualCall` делает три шага: разыменовать таблицу, взять указатель,
  позвать. Сколько из них делает `shape->Area()`?
- Что в ручной версии проверяет компилятор, а что нет? Например: можно ли
  случайно положить в таблицу квадрата функцию площади прямоугольника?

**Про замер отдельно.** Если ваше объяснение звучит как «`virtual` медленнее,
потому что косвенность», проверьте его числами: на этом замере оно
не подтвердится, и это самое полезное, что отсюда можно вынести. Обратный
вывод — «`virtual` бесплатен» — тоже не следует. Цена вызова здесь доли
наносекунды, а рядом с ним стоят тело метода длиннее одной операции
и обращения в память вразнобой; они её и съедают. Чтобы разница стала видна,
между двумя ветками замера должен отличаться **только** вызов — и размещение
объектов в памяти, и порядок обхода одинаковы. Такой замер построить можно, и вопрос
«а на чём тогда это видно» стоит задать вслух.

## Почему так устроено

Читать не обязательно, чтобы сдать занятие, но на проверочной об этом
спрашивают.

### Чем `IRule` отличается от `RuleBase`

`IRule` отвечает на вопрос «что правило умеет»: только чисто виртуальные
функции и ни одного поля. Это контракт, и движок разговаривает с правилами
только через него. `RuleBase` отвечает на вопрос «что у всех правил
одинаково»: идентификатор, важность, действия, счётчик. Это общий код, а не
контракт.

Меняются они по разным причинам. Правило, которому не нужен счётчик,
унаследует `IRule` напрямую. Новое поле, общее для всех правил, добавится
в `RuleBase`, и движок этого не заметит.

### Почему правила хранятся указателями

На 2.2 правила хранились `std::vector<MatchRule>`, потому что
в `std::vector<RuleBase>` от наследника доехала бы только базовая часть —
[срезка](../lectures/glossary.md#slicing) (object slicing),
[постановка 2.2](2.2.md#почему-правила-хранятся-вектором-matchrule).
`std::vector<IRule>` не собрать вовсе: `IRule` абстрактен, и объект такого
типа создать нельзя. Указатель срезать нечего, он одного размера при любом
наследнике. Поэтому движок хранит `std::vector<std::unique_ptr<IRule>>`,
и в одном векторе лежат и `MatchRule`, и `SequenceRule`.

Цена видна сразу: аллокация на каждое правило и условие и косвенный вызов
на каждую проверку. Стоит ли она того — вопрос, на который отвечает
[упражнение](#упражнение-диспетчеризация), и ответ там может оказаться
не тем, которого вы ждёте.

### Почему у интерфейса виртуальный деструктор

`std::unique_ptr<IRule>` удаляет правило через указатель на `IRule`. Если
деструктор `IRule` не виртуальный, вызовется только он, а деструктор
`MatchRule` — нет: вектор условий не освободится. Сам `delete` при этом
передаёт размер `IRule`, а выделялся объект размером с `MatchRule`, —
именно это санитайзер и называет `new-delete-type-mismatch`.

**Правило:** у класса, который удаляют через указатель на базу, деструктор
базы виртуальный ([лекция 7, раздел 5](../lectures/07/lecture.md#5-виртуальный-деструктор)).

### Почему движок не печатает

Движок отвечает на вопрос «какие правила сработали на этом событии», а что
делать с ответом, решает тот, кто спрашивает. На 1.3 печать жила в
`CheckRules`, на 2.2 переехала в агента, а теперь движок о ней не знает
вовсе. Поэтому его можно проверить тестом без перехвата вывода и позвать
из кода, которому печать не нужна.

### Почему у правила с состоянием есть вытеснение

`SequenceRule` помнит каждый первый шаг, пока не придёт второй. Первых шагов
в потоке много, вторых мало, и без вытеснения память правила растёт всё
время, пока агент жив, — а агент работает неделями. Правило при этом
срабатывает правильно, и ошибка не видна ни в одном выводе. Её показывает
только тест на сотне событий и `pending()`.

### Почему пустой `AnyOf` — ложь

«Все из ничего выполнены» — верное утверждение, поэтому пустой `AllOf`
возвращает `true` и ничего не меняет внутри другого `AllOf`. «Хотя бы одно
из ничего» — неверное. Если бы пустой `AnyOf` возвращал `true`, правило,
у которого забыли заполнить варианты, срабатывало бы на каждом событии.
С `false` оно молчит, и забытое видно в сводке по нулю детектов.

### Почему правила проверяют на чужих журналах

Семь открытых сценариев — не весь набор: правила агента прогоняются ещё и
на журналах, которых у вас нет, и качество считается по точности и
полноте. Правило, подогнанное под конкретный журнал, на незнакомом
развалится. Поэтому оба шага правила стоит описывать по смыслу атаки, а не
по строкам, которые видно в `phishing_macro`.

### Почему набор 2.2 отключён

Предмет набора 2.2 — `Condition` с переключателем вида сравнения и вектор
правил конкретного типа. На этом занятии не остаётся ни того, ни другого, и
проверять там нечего. Набор 2.1 наоборот остаётся: условия переписаны
целиком, но `operator()` у них сохранён. Если что-то из набора 2.1
покраснело, вместе с формой условия изменилось его поведение, а этого
не требовалось.
